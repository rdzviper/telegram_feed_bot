# Telegram Feed Bot — Техническая спецификация

## Описание

Personalized feed-агрегатор для Telegram. Userbot (от лица пользователя) читает новые посты из подписанных им каналов, анализирует через DeepSeek, оценивает релевантность на основе матрицы пользовательских интересов, и форвардит релевантные посты в личный notify-чат.

## Проблемы которые решает

1. **Информационная перегрузка** — подписано на 50+ каналов, не успеть читать всё
   - Решение: автоматическая фильтрация по релевантности

2. **Дублирование контента** — одна новость в разных каналах/разных словами
   - Решение: локальная дедупликация по Jaccard между концептами поста и концептами уже пересланных постов за N часов (не DeepSeek — он ненадёжно ловил дубли)

3. **Реклама и спам** — каналы постят коммерческие посты
   - Решение: автоматический детекция is_ad, пропуск

4. **Холодный старт** — как начать фильтровать если система не знает вкусы
   - Решение: адаптивный порог, всё форвардится пока нет интересов, затем автоматическое обучение через 👍/👎

5. **Контекстные и составные интересы** — интерес зависит от СВЯЗКИ концептов, не от одного (примеры принёс Алекс 2026-07-15)
   - Интересны изменения ставок ВТБ, но НЕ лайфстайл-события ВТБ (Family Day), и НЕ ставки Сбербанка
   - Интересна техника (авто, видеокарты), но НЕ новости про MacBook — КРОМЕ MacBook в связке с AI/LLM-производительностью
   - Текущая аддитивная модель весов по концептам это не выражает: у концепта один вес на все контексты, «И» и смена знака от соседнего концепта невозможны. Требует семантики поста + entity-слоя — см. раздел «Единый семантический слой (2026-07-15)»

## Входные требования

- TG_API_ID, TG_API_HASH — credentials Telegram приложения
- Session-файл (.session) — сохранённая авторизация userbot (от лица пользователя)
- BOT_TOKEN — токен вспомогательного Telegram-бота для отправки сообщений
- NOTIFY_CHAT_ID — чат куда форвардятся посты (обычно личный чат с ботом)
- ALLOWED_USER_ID — ID пользователя (для проверки авторизации команд)
- DEEPSEEK_API_KEY — API-ключ для анализа текстов

## Архитектура

### Компоненты

| Модуль | Назначение |
|--------|-----------|
| `bot.py` | Точка входа. Инициализирует Telethon userbot (от лица пользователя через session + API credentials), регистрирует обработчики входящих сообщений, синхронизирует диалоги. Входящие события кладутся в `asyncio.Queue`, единственный `pipeline_worker` обрабатывает их строго по одному (гарантия порядка forward → голосовалка) |
| `pipeline.py` | Основной pipeline: анализ поста → scoring → дедуп → форвард → сохранение в БД |
| `analyzer.py` | Вызов DeepSeek для извлечения концептов и детекции is_ad |
| `handlers.py` | Обработчики Telegram-команд (`/stats`) и кнопок (👍/👎) |
| `database.py` | SQLite ORM. Таблицы: messages, channels, interests |
| `config.py` | Конфиг: API-ключи, пороги, пути |
| `plugins/` | Плагины сырого роутинга — bypass основного пайплайна для избранных источников (см. «Плагины: сырой роутинг») |

### Поток данных

```
Telethon (userbot)
    ↓ получает posts от каналов → asyncio.Queue
pipeline_worker (по одному событию)
    ↓ вызывает DeepSeek
DeepSeek API
    ← вернул: concepts, is_ad
Local Scoring
    ↓ суммирует веса концептов из матрицы (unknown = 0.15)
Adaptive Threshold
    ↓ сравнивает score с avg(last 200)
Dedup (Jaccard)
    ↓ сравнивает концепты с пересланными за DUPLICATE_HOURS
Decision
    ├─ is_ad → пропуск
    ├─ same_story (Jaccard ≥ порог) → пропуск
    ├─ score < threshold → пропуск (или drift)
    └─ score ≥ threshold → форвард в notify_chat
Delivery
    ← Telethon forward_messages (нативный форвард поста, медиа/альбомы/форматирование)
    ← Bot API send_message (голосовалка: концепты+веса, Σ, порог, кнопки 👍/👎)
Handlers
    ← пользователь нажал 👍/👎
Update Interests
    ← концепты +1.0 (лайк) или -0.3 (дизлайк)
```

## Алгоритм

### 1. Холодный старт (интересов = 0)

- Пороговый threshold = avg(last 200 seen posts) = 0
- Все посты (score ≥ 0) форвардятся
- Пользователь начинает лайкать → концепты накапливаются в interests

### 2. Адаптивный порог

```python
threshold = avg(local_score for last 200 posts)
forward if local_score > threshold
```

Система автоматически подстраивается: чем популярнее интересы, тем выше порог.

### 3. Локальный scoring

```python
concepts = DeepSeek.extract(text)
weights = db.get_weights(concepts)  # {topic: float}
local_score = sum(weights[c] for c in concepts)
```

Если концепт не в матрице → вес 0 → не влияет на score.

### 4. Drift-механизм

Каждые N постов (конфиг `DRIFT_EVERY_N`, дефолт 20) один пост форвардится **вне зависимости** от score. Нужен чтобы:
- Обучить бота на новые темы
- Разбавить монотонность в случае очень узких интересов

Drift-пост помечается 🔍 эмодзи.

### 5. Дедупликация (локальный Jaccard)

После получения концептов от DeepSeek сравниваем множество концептов текущего поста с концептами каждого пересланного поста за последние `DUPLICATE_HOURS` часов:

```python
jaccard = |A ∩ B| / |A ∪ B|
if jaccard >= DUPLICATE_JACCARD_THRESHOLD:  # дефолт 0.5
    same_story = True  # пропуск
```

Полностью локально, без API-вызовов (пересечение множеств строк). Заменил ненадёжный DeepSeek-детектор.

**Известная слабость метрики:** зависит от консистентности концептов. Если один пост дал `бездомный кот`, другой `кот` — пересечение падает. Решается промптом (убирать описательные прилагательные, но сохранять устойчивые термины типа «кредитная карта»). Альтернатива на будущее — Overlap coefficient `|A∩B| / min(|A|,|B|)` вместо Jaccard, лучше ловит дубли где один пост краткий, другой развёрнутый.

### 6. Фильтры

- **is_ad**: реклама, промо, партнёрский контент, призывы купить/подписаться, сбор пожертвований/донатов (включая благотворительные) → пропуск
- **same_story**: Jaccard-дубль за последние DUPLICATE_HOURS → пропуск (даже если score высокий)
- **is_channel_active**: канал отключен через `/stats` → пропуск
- **rate_limit**: не более N постов в час → пропуск (конфиг `RATE_LIMIT_PER_HOUR`, дефолт 20)

## Форвард

**Два сообщения в notify-чат, строгий порядок:**

1. **Нативный форвард** через `tg_client.forward_messages()` (от лица userbot) — сохраняет медиа, альбомы (несколько картинок), форматирование, "Forwarded from". Решает разом проблемы download/upload-таймаутов больших видео и потери форматирования.
2. **Голосовалка** через Bot API `send_message()` — отдельное сообщение с кнопками 👍/👎 (кнопки может слать только бот, не userbot).

Порядок гарантирован тем, что оба `await` идут последовательно в одном `pipeline_worker`, а события обрабатываются по одному через очередь.

### Содержимое голосовалки

Сейчас (режим отладки/обучения) — показывает разбор скоринга:
```
Госдума +0.30  ·  измена +0.80  ·  кот +0.15
Σ 1.45  порог 0.50
👍  👎
```
Каждый концепт с текущим весом (`+0.15` = ещё не обучен, дефолт для unknown). Позволяет видеть, как голос отразится на будущих постах.

**История вариантов плашки** (обсуждалось, отклонено):
- `text=""` / zero-width space → Bot API отклоняет («Text must be non-empty»)
- `・・・・・・・・・・` (японские точки) → не понравилось визуально
- Ссылка на канал `<a href>Название</a>` → кандидат на будущее, когда обучение стабилизируется

### Кнопки

- 👍 `like:{msg_id}` — +1.0 к весам всех концептов поста
- 👎 `dislike:{msg_id}` — -0.3 к весам всех концептов поста (асимметрия: лайк весомее)

Защита от повторного голоса (`get_user_choice`). После голоса кнопки убираются, добавляется метка ✅/❌. Оба варианта обновляют счётчики канала.

## Плагины: сырой роутинг (реализовано 2026-07-30)

Отдельная от feed-пайплайна задача: часть источников нужно **пересылать целиком, без анализа**, в собственное хранилище отдельного агента-потребителя (напр. finance-агент), который сам вычитывает и чистит за собой. Никакого DeepSeek/scoring/dedup — это не feed, это сырой канал доставки.

### Архитектура

`on_new_message` в `bot.py` матчит `event.chat_id` по карте `plugin_channel_map` **до** входа в основной пайплайн и **до** фильтра `event.message.post`:
- источник плагина может быть не только broadcast-каналом (`post=True`), но и чатом/мегагруппой (`post=False`, напр. `@stavkivklad` — чат ~10к участников). Проверка типа сообщения матчится позже, только для не-плагинных источников;
- если чат/канал совпал с картой плагинов — сообщение уходит в `plugin.handle(event)` и в основной пайплайн (scoring/dedup/forward в notify-чат) **не попадает**;
- иначе — как раньше, в `asyncio.Queue` → `pipeline_worker`.

```
Telethon (userbot)
    ↓ NewMessage event
chat_id в plugin_channel_map?
    ├─ да → plugin.handle(event) → своя БД, END (bypass пайплайна)
    └─ нет → фильтр event.message.post → очередь → pipeline_worker (как раньше)
```

### Контракт плагина (`plugins/base.py`)

```python
class FeedPlugin:
    name: str
    source_channels: list[str]        # usernames без @

    async def setup(self, client):    # резолвит usernames → channel_id (utils.get_peer_id),
                                       # вызывается один раз после tg_client.start()
    async def init_storage(self): ...
    async def handle(self, event): ...
```

### Загрузчик (`plugins/__init__.py`)

`load_plugins()` сканит модули в `plugins/`, забирает объект `PLUGIN` из каждого. Нет модуля / нет `PLUGIN` — функционала нет, бот работает как раньше. Отключение без удаления файла: `PLUGIN_<NAME>_ENABLED=0` в `.env`.

### Плагин `finance` (`plugins/finance.py`)

- **Источники**: `stavkivklad`, `hranidengi`, `blogbankir`, `invest_banks` (первый — чат 10к людей, не канал; см. bypass выше).
- **Фильтр**: только непустой `event.message.text` (включая подпись под медиа); чистое медиа без подписи — пропуск.
- **Хранилище**: отдельный SQLite-файл `data/finance_feed.db` (WAL), НЕ основная БД бота.
  ```sql
  CREATE TABLE messages (
      id INTEGER PRIMARY KEY AUTOINCREMENT,
      source_channel TEXT NOT NULL,
      message_id INTEGER NOT NULL,
      text TEXT NOT NULL,
      created_at TEXT DEFAULT (datetime('now')),
      UNIQUE(source_channel, message_id)   -- идемпотентность на рестарте

  ```
- **Хэндофф потребителю** (finance-агент ходит на VPS по SSH, чекпойнтит WAL на самом хосте — не копирует .db-файл вслепую):
  ```sql
  BEGIN IMMEDIATE;
  SELECT id, source_channel, text, created_at FROM messages ORDER BY id;
  DELETE FROM messages WHERE id <= :max_взятый_id;
  COMMIT;
  ```
  Потребитель владеет удалением — producer (плагин) только пишет.

Копия `finance.py`: свой `name`, свой `source_channels`, своя `*_feed.db`. `load_plugins()` подхватывает автоматически, правок в `bot.py` не требуется.

## Требования к DeepSeek

### Запрос `analyze(text)`

Входные параметры:
- `text`: текст поста (до 1500 символов)

`recent_headlines` и `same_story` убраны — дедупликация теперь локальная (Jaccard).

Ожидаемый ответ (JSON):
```json
{
  "concepts": ["Sony", "игра", "цены"],
  "is_ad": false
}
```

Вызывается с `extra_body={"thinking": {"type": "disabled"}}` — критично: `deepseek-v4-flash` по умолчанию включает thinking-режим, который съедает `max_tokens` на reasoning и возвращает пустой content. `max_tokens=150`, `temperature=0`, `response_format=json_object`.

**Правила нормализации концептов:**
- Именительный падеж, единственное число
- Одна каноническая форма: "сони" → "Sony", "игры" → "игра"
- Убирать описательные прилагательные, не меняющие смысл: "бездомный кот" → "кот"
- Сохранять прилагательные в устойчивых терминах: "кредитная карта", "ядерное оружие"
- Игнорировать шутки/иронию/метафоры ("Кошачья служба" — не концепт)
- 3–7 концептов
- Исключить стоп-слова ("новость", "рынок", "компания", "мероприятие")

## Поведение холодного старта

**День 1–2:** Пользователь видит все посты. Нажимает 👍 на интересные.

**День 3+:** После ~5–10 лайков начинает формироваться матрица. Пороги становятся строже автоматически. Пользователь видит преимущественно релевантные посты, но drift каждые N постов всё ещё позволяет обнаружить новые темы.

## Граничные случаи

### 1. Новый концепт без история

Концепт с weight=0 не влияет на local_score. Пост где есть новый концепт + известные получит score только от известных.

### 2. Концепты с очень разными весами

Если "Sony" имеет weight=50, а "цены" — weight=1, их сумма даст правильный score, но посты про "Sony и цены" будут доминироваться одним концептом. Это корректное поведение — пользователь явно выбрал через лайки.

### 3. Очень узкие интересы (все концепты > threshold)

Drift механизм спасает: раз в N постов один пройдёт, даже если score низкий.

### 4. Адаптивный порог упирается в ноль

Если ВСЕ последние 200 постов имели score < 0 (много дизлайков), то threshold может быть отрицательным. Посты с score ≈ 0 начнут проходить. Это нормально — система восстанавливается.

## Расширения (future)

- Decay весов со временем (старые интересы медленно теряют влияние)
- Cluster концептов (синонимы "Сони", "Sony", "Sony Interactive" → одна группа)
- Командные интересы (группа может совместно обучать бота)
- Экспорт интересов / резервная копия матрицы

### LLM-verify для серой зоны cosine (идея 2026-07-30)

**Проблема:** Кластеры 5/6/7 в `tests/dedup_cases.md` (Wolverine, рынок труда,
Machine Party) — реальные дубли, но их cosine стабильно ложится в диапазон
**0.6–0.75**: не мусор (совсем разные темы дают cosine существенно ниже), но
и не долетает до порога 0.72–0.75. Эмбеддинг короткой canonical-summary
теряет нюанс, когда дубли расходятся в деталях (платформа/автор/имя).

**Идея:** второй слой поверх текущего cosine, без замены его:
1. Cosine считается как сейчас — бесплатно (numpy, уже готовые вектора).
2. Если cosine попал в серую зону (~0.55–0.72) — **точечный LLM-вызов**:
   отдать DeepSeek только 1–2 постов-кандидата (не весь пул), спросить
   «это одна и та же история?». НЕ пихать весь день/пул сразу — оценивали
   вариант «весь день одним запросом»: токены не проблема (DeepSeek-v4-flash
   $0.14/1M input, реалтайм-пул ~390 forwarded/день ≈ центы), но (а) ломает

### Альтернативная формула порога (идея 2026-07-10)

Вместо `AVG(local_score за последние 200 постов)` считать порог как ожидаемый score случайного поста из матрицы:

```python
threshold = max(0, AVG(weight по всем топикам в interests)) * AVG_CONCEPTS
# AVG_CONCEPTS — константа ≈ 5 (среднее число концептов на пост)
```

**Смысл:** пост проходит, если его score выше того, что получил бы «средний» пост на текущей матрице интересов.

**Плюсы:** не загрязняется неоценёнными постами; зависит только от матрицы; реагирует ровно при голосовании; прозрачная семантика; работает с нуля без прогрева.

**Минусы:** при большом количестве дизлайков средний вес уходит в минус → `max(0, ...)` нужен; нестабилен при маленькой матрице (10 топиков — один лайк сильно дёргает порог); AVG_CONCEPTS как константа создаёт перекос для постов с 3 или 7 концептами.

**Текущее решение предпочтительнее** пока матрица мала. Вернуться к этой идее, когда накопится 100+ оценённых топиков.

### Архитектура голосования per-topic (идея 2026-07-10)

**Вместо:** кнопки 👍/👎 на все концепты поста сразу.

**Новая схема:**
- Селектор который раскрывает список концептов поста (коллапс/ експанд)
- Каждый концепт отдельно — свой лайк (дизлайк убрать, только +1)
- **Пересчёт порога:** не `AVG(local_score последних 200)`, а `AVG(weight всех топиков) × N_concepts`
  - Порог становится свойством матрицы, не истории
  - Чем популярнее интересы → выше среднее → выше порог → остальные автоматически понижаются в приоритете
  - Реагирует ровно на голоса, без фантомного drift

**Вопрос дизайна:** если только лайки без дизлайков?
- Матрица расходится: каждый топик тренируется только в +1 → со временем веса ползут в бесконечность
- Защита: `max(0, AVG(weights)) × N` даст порог который вырастет пропорционально
- **Но если все топики на +1, дифференциация теряется** → порог вырастет как и веса → всё равно не проходит больше
- Нужны дизлайки (−0.3) для баланса
- **Альтернатива:** нормализованный score = `weight / AVG(weights)`, тогда средний score = 1, дизлайки не нужны (редкий топик падает за счёт роста других). Красивее, но переделка архитектуры.

**Статус:** идея, требует апробации на 50+ постах перед внедрением.

### Отказ от отдельного notify-чата → доставка в DM с ботом (идея 2026-07-10)

**Сейчас:** userbot форвардит в отдельный `NOTIFY_CHAT_ID`, бот шлёт туда голосовалку.

**Идея:** убрать отдельный чат, слать всё прямо в личный диалог userbot↔bot. `NOTIFY_CHAT_ID` = id этого DM.

**Механика (проверено концептуально, работает):**
- userbot форвардит пост в `get_input_entity(bot)` — аккаунт спокойно шлёт ботам, форвард с медиа/альбомами/«Forwarded from» сохраняется.
- бот получает этот форвард как входящий update — игнорирует (хендлеры только команды и callback'и, петли нет).
- бот шлёт голосовалку в тот же DM.
- userbot метит DM непрочитанным.

**Почему работает (разбор прежних ложных возражений):**
- **mark-unread работает.** Уже сейчас userbot форвардит от своего имени и сам же шлёт `MarkDialogUnreadRequest(unread=True)` — флаг держится до открытия диалога, независимо от автора последнего сообщения. В DM с ботом идентично. Тезис «не работает на свои сообщения» — ложный.
- **Порядок гарантирован.** `asyncio.Queue` + единственный `pipeline_worker` держат порядок наших `await`, а не порядок в чате. Форвард → голосовалка последовательны в воркере в любой чат.
- **Уведомления.** Сообщения бота (голосовалка) триггерят notification в DM — пост не пропустишь даже без mark-unread. mark-unread становится бонусом.

**Цена (обратимая):** история DM смешивается с `/stats`, системными сообщениями и голосовалками. Подчищается вручную при желании.

**Выигрыш:** минус одна сущность (отдельный чат/канал), логика та же.

**Статус:** жизнеспособно. Внедрение = смена `NOTIFY_CHAT_ID` на id DM + форвард в input-entity бота.

**⚠ Ревизия 2026-08-05 — прямой форвард юзерботом в DM не работает, нужен транзитный хоп.**

Пробовали вживую (`tgfeed-probes/probe1-4`) и выяснили, почему одного хопа недостаточно:

1. **Бот не может форвардить из источников.** Бот не состоит в подписанных каналах/чатах Алекса — по правилам Telegram он не может форвардить оттуда, где не участник. Форвардить из источника может только юзербот (аккаунт Алекса, он там подписан).
2. **Прямой форвард юзерботом в целевой чат ломает отслеживание непрочитанного.** Это исходящее сообщение от **своего же** аккаунта → все клиенты Алекса синхронизируются на последнее сообщение как прочитанное, непонятно что реально не читал (ровно то, что описывала идея выше — «чат проматывается к самому последнему»).
3. **Принудительная пометка непрочитанным не спасает.** `MarkDialogUnreadRequest` технически работает (см. пункт «mark-unread работает» выше), но эмпирически десктопный клиент Telegram **теряет фокус на чате**, когда это происходит — мешает читать. Тезис «работает» из идеи 2026-07-10 верен технически, но с этим побочным эффектом непригоден на практике.

**Решение — два хопа, разные идентичности (не один, как предполагалось):**

```
Источники (каналы/чаты, Алекс подписан)
    ↓ форвард ТОЛЬКО юзерботом (единственный, кто там участник)
"Telegram feed" (транзитный канал — Алекс не читает его вживую,
                  scroll-to-bottom/unread здесь не важны)
    ↓ бот (отдельная Bot API идентичность) вычитывает и репостит
Приватный чат Алекс ↔ бот
    ↓ Алекс реально читает и реагирует ЗДЕСЬ
```

Второй хоп делает **бот**, а не юзербот — для Алекса это настоящие входящие сообщения (не «свои»), обычный unread/notification работает без спецхаков и без потери фокуса.

**Бонус — открывает нативные реакции (пробы 3-4, 2026-08-05, см. `probe3_reactions.py`/`probe4_reactions_dm.py`):** в приватном чате Алекс↔бот Bot API отдаёт полноценный `message_reaction` (конкретный юзер, discrete `old_reaction`→`new_reaction`), в отличие от канала-хопа (`message_reaction_count` — анонимный агрегированный счётчик, без актёра). Значит именно на втором хопе реакции могут заменить кнопки 👍/👎 из раздела «Кнопки» выше.

**Статус:** архитектура (два хопа + реакции на втором) зафиксирована по итогам живых проб. Детальный дизайн реализации (обработчик второго хопа, маппинг эмодзи→delta, миграция с `CallbackQueryHandler` на `MessageReactionHandler`) — следующий шаг, код не писать до отдельного апрува дизайна.

### Векторный дедуп (план перехода, идея 2026-07-10)

**Проблема:** дедуп по overlap концептов фундаментально хрупкий. Реальные провалы (см. `tests/dedup_cases.md`):
- **Verbatim-репост** (идентичный текст, идентичные концепты) не схлопнулся — баг видимости/порядка; но verbatim вообще не должен зависеть от концептов.
- **Та же новость другими словами** (`Wildberries`↔`маркетплейс`, `бензин`↔`топливо`, `SIM` латиница vs `сим` кириллица) → overlap концептов ≈ 0. DeepSeek на одну новость выдаёт разные наборы концептов — опираться на них для дедупа нельзя.

**Ключевой принцип: дедуп и вкус — ортогональны.**
- **Вкус/релевантность** (форвардить ли): концепты → веса → score vs порог. Голос 👍/👎 двигает веса концептов. Интерпретируемая votable-матрица («Wildberries +0.68»).
- **Дедуп** (не повтор ли): вектора. К вкусу отношения не имеет.

Вектор — точка в N-мерном пространстве, ему нельзя присвоить понятный вес. Отличен для «похожести», плох как votable-модель. **Поэтому: вектора → только дедуп; концепты → вкус и голосование остаются без изменений.** Плашка с весами сохраняется. При схлопывании дублей голос идёт за концепты выжившего поста.

Векторный вкус (content-based рекомендатор: центроиды лайков/дизлайков, score = cosine-разница) — возможен, но непрозрачен (нет объяснимых весов, размывается мультимодальный вкус). Держим как отдельный поздний эксперимент, не ценой потери прозрачной матрицы.

**Целевой стек дедупа:**
```
DeepSeek: concepts + is_ad + informative + summary (1 нейтральная строка сути события)
      ↓
дешёвый текстовый pre-filter (нормализация: lower, срез эмодзи/URL/пунктуации,
   фолдинг латинско-кириллических двойников, множество слов, overlap coefficient)
   → ловит verbatim-репосты за ноль стоимости
      ↓
локальный multilingual-эмбеддинг summary (напр. intfloat/multilingual-e5-small,
   384-dim, ~470MB, CPU; альтернативы: paraphrase-multilingual-MiniLM,
   rubert-tiny2 если контент почти весь RU, bge-m3 для топ-качества)
      ↓
cosine vs summary-вектора forwarded за DUPLICATE_HOURS (numpy in-memory,
   окно = десятки-сотни векторов, вектор-БД не нужна)
   → cosine ≥ порог (~0.80–0.88, калибровать на tests/dedup_cases.md) = дубль
```

**Что эмбеддить:** саммари от DeepSeek, не сырой текст — убирает филлер («чехлы застряли в поле»), фокус на событии. Синонимы (`Wildberries`≈`маркетплейс`) ловятся самим векторным пространством, явные маппинги не нужны.

**Хранение:** вектор BLOB'ом в `messages`. Апгрейд при росте — `sqlite-vec` (векторный поиск прямо в существующем SQLite, стек не меняется); дальше faiss/hnswlib/qdrant/pgvector — оверкилл.

**API-эмбеддинги** (Jina v3, Cohere multilingual-v3, OpenAI text-embedding-3-small) — отвергнуты: per-call плата против стиля pay-as-you-go/free; локальная модель бесплатна и приватна. DeepSeek отдельного embeddings-эндпоинта, по-видимому, не имеет — проверить перед выбором.

**Статус:** план. Тест-сет для калибровки порога — `tests/dedup_cases.md` (пополняется реальными примерами).

**Новые боевые примеры (принёс Алекс):**

**Инсайт Алекса:** дедуп и релевантность — это один вопрос семантической близости («насколько пост по смыслу близок к чему-то»): дедуп — к недавно пересланному, релевантность — к вкусу. Значит, единый механизм = эмбеддинги. Это **частично пересматривает «дедуп и вкус ортогональны» (2026-07-10)**: вектора теперь и для вкуса (content-based из лайков), не только дедуп. Интерпретируемая votable-матрица концептов уступает место семантике — принимается сознательно.

**Железо (проверено 2026-07-15):** VPS 4GB RAM / 10GB NVMe, шаренный с traefik/3x-ui/amnezia (VPN, CPU-чувствительны).

- **Пересматривает вывод 2026-07-10 «API-эмбеддинги отвергнуты»:** на этом железе API предпочтительны — footprint ~ноль (ни диска, ни RAM, ни CPU), качество выше tiny, цена ~центы/мес на текущем объёме (~сотни постов/день), latency +~100мс неважна. Провайдер: у DeepSeek embeddings-эндпоинта, по-видимому, нет (подтвердить) → OpenAI-совместимый `text-embedding-3-small` (тот же `AsyncOpenAI` клиент, другой base_url/key) / Jina v3 / Cohere multilingual-v3.

**Реклама (Q Алекса):** эмбеддинги is_ad НЕ решают — реклама это интент/прагматика («подписывайся», инвайт t.me/+…, нативка), а не тема; семантически рекламный пост может совпадать с обычным. **is_ad остаётся на DeepSeek** (+ дешёвые регексп-правила на инвайт-ссылки). Ещё один довод не выкидывать DeepSeek.

**Обучение — только лайки, без текстовых интересов (решение Алекса):**
- Прототипы pos/neg растут только из 👍/👎; cold-start как сейчас (льём всё), сходится медленнее без seed-фраз, способность не теряется.
- Для контекстных связок (MacBook+AI) учить на эмбеддинге ПОСТА (несёт контекст), не голого слова-топика (у одного слова контекста нет).
- Пер-топик голоса → кормят **entity-слой** (ВТБ vs Сбербанк, где эмбеддинг размывает сущность). Гибрид: сущности из DeepSeek-концептов + семантика из эмбеддинга поста.
- Чем лучше эмбеддинг — тем меньше примеров нужно на разделение тонких случаев → при «только лайки» (разметки мало) это доп. довод за API, а не tiny.

**Целевая формула релевантности:** kNN/центроиды pos/neg прототипов из лайков; `score = sim(pos) − λ·sim(neg)` vs порог. Заодно пересмотреть порог/unknown-boost (симптом: посты кластера GitHub Σ≈4.25/4.24 впритык).

**План фазами:** Фаза 1 — дедуп на эмбеддингах (низкий риск, чинит GitHub-кейс, обкатка API-слоя, Jaccard как дешёвый предфильтр). Фаза 2 — релевантность на прототипах + entity-слой.

```
     → дубль, если сработал любой слой
```

**Отказоустойчивость:** ошибка эмбеддинг-API → `embed`=None → работает слой 0, пост не теряется. Latency +~100мс/пост (summary бесплатно в существующем вызове). Локальной модели нет, `mem_limit` не трогаем.

**Edge-cases (принято для A1):** развязка/опровержение (РКН 3g) склеится с сюжетом; отрицание — слабость эмбеддингов, не лечим; медиа — дедуп по тексту саммари.

**Шаги:** (1) `summary` в analyzer; (2) `embeddings.py`+конфиг+колонки БД; (3) калибровка → порог; (4) врезка в pipeline, concept-overlap убрать; (5) наблюдение на 4 кластерах + живом потоке.

**Калибровка (прогон 2026-07-16, small/512 vs 1536 vs large/1536):** классы **перекрываются** — `min(внутри)≈0.51`, `max(между)≈0.63` (кластер Минцифры-блокировки ≈ кластер GitHub-блокировки: разные события, но оба «Россия блокирует»). Идеального порога нет. Последовательный охват при 0 ложных склеек: пик ~56% (small/512, τ=0.78), ~33% при строгом τ=0.80. Больший эмбеддинг (large/1536) лучше разводит *разные* события (max между 0.63→0.55), но охват не поднимает. **Вывод: реальный рычаг — каноничность `summary`, не модель/размерность.** Оставлен small/512. Текстовый предфильтр (слой 0) ловит verbatim независимо.

**Тюнинг summary (2026-07-16) — подтвердил вывод:** переписан промт summary на жёсткий формат «<место>: <именованные сущности> — <действие>» с обязательными каноничными сущностями (v2). Результат на том же сете: `min(внутри)` 0.51→0.585, посл. охват при 0 ложных склеек — **78% @ τ=0.75, 100% @ τ=0.72** (было 33–56%). Попытка убрать общие слова (v3) сделала хуже (общие «блокировка/доступ» держат посты одной новости вместе) — откатили к v2. Старт `DUPLICATE_COSINE_THRESHOLD=0.75` (строгий, дубли допустимы, отрыв 0.105 от худшей чужой пары 0.645); крутить 0.72–0.80 через `.env`.

### A2 — Вкус вектором (направление, 2026-07-15)

Пересматривает «вектор-вкус хуже» (2026-07-10): дискретные веса по концептам НЕ выражают контекст/связки (Проблема 5), поэтому интерпретируемость защищать нечего.
- Вкус = прототипы pos/neg из **эмбеддингов саммари**, обучение с лайков/дизлайков **на пост целиком**; `score = sim(pos) − λ·sim(neg)`.
- Гибрид: вектор — семантика/контекст; тонкий entity-слой из концептов — сущностные правила (ВТБ vs Сбербанк).
- Синергия: те же вектора, что и в A1 (дедуп сравнивает с форвардами, вкус — с прототипами лайков). A1 — фундамент.
- UI-следствие: голос переезжает на пост (по саммари), пер-топик UI → entity-слою или убирается.
- Цена: теряется объяснимая матрица весов (осознанно).
- Статус: направление; детальный дизайн — после A1.

# Роадмап: Watchlist-режим (распродажи) и модульная архитектура

> Обсуждение 2026-07-08. Пока **не реализовано**, зафиксирован дизайн, чтобы не терять контекст.

## Задача

Помимо ленты новостей (feed), пользователь хочет отслеживать **распродажи/предложения** по конкретным сущностям:
- конкретный товар: `PlayStation 5` (не просто `PlayStation`)
- авиабилеты по направлению **из Самары** в конкретный город (Москва, СПб), с потолком цены
- при этом другие направления/товары интересуют меньше, но могут стать интересны в будущем

## Почему текущая feed-архитектура не подходит напрямую

| Проблема | Суть |
|----------|------|
| **Гранулярность концептов** | feed нормализует к каноничной форме (`PlayStation`, `авиабилет`). Для распродаж важна конкретика (`PlayStation 5`) и **связки** (`Самара→Москва`). Отдельные концепты `Самара +0.8` и `Москва +0.5` не отличают рейс Самара→Москва от Москва→Самара |
| **Пороговая модель** | adaptive threshold = avg последних 200 постов, заточен под плотный однородный поток новостей. Трафик распродаж рваный — порог пляшет |
| **Jaccard-дедуп вреден** | две разные распродажи PS5 в разных магазинах — оба ценны (сравнить цены), а Jaccard посчитает дублем |
| **Origin-фильтр — это правило, не вес** | «только из Самары» — жёсткое must-have условие (булева логика), матрица весов такого не умеет |

**Вывод:** это другая задача — не «ранжирование потока по обучаемому вкусу», а «watch-лист сущностей с параметрами» (товар + цена<X, направление + город вылета).

## Выбранное направление: модульная стратегийная архитектура (вариант B)

Часть каналов матчится на стратегию `feed`, часть на `watchlist`. Ingest, delivery, storage, feedback-loop — общие. Различается только «мозг» решения.

### Общее ядро (не зависит от стратегии)
- **Ingest**: Telethon userbot, очередь, фильтр `event.message.post`, отсев по already-seen
- **Delivery**: нативный форвард + голосовалка, редактирование после голоса
- **Storage**: messages, channels, БД-слой
- **Feedback**: 👍/👎 → callback → `strategy.on_vote()`
- **DeepSeek клиент** (транспорт; промпт у каждой стратегии свой)

### Интерфейс стратегии
```python
class Strategy:
    async def analyze(text) -> dict            # свой DeepSeek-вызов/парсинг
    async def should_forward(analysis, channel) -> Decision
    async def on_vote(msg_id, choice)          # своё обучение/состояние
    def render_vote_panel(analysis) -> str     # содержимое плашки кнопок
```

`process_message` после рефакторинга:
```python
strategy = registry.for_channel(channel_id)      # feed | watchlist
analysis = await strategy.analyze(text)
decision = await strategy.should_forward(analysis, channel_id)
if decision.forward:
    await deliver(event, strategy.render_vote_panel(analysis))  # общее
```

`handlers.py` при голосе: `strategy = registry.for_message(msg_id); await strategy.on_vote(...)`.

### Различия стратегий

| | feed | watchlist |
|---|---|---|
| Извлечение | concepts | структура: товар / направление / цена / город |
| Решение | score ≥ adaptive threshold | матч правил (origin=Самара, price<X) |
| Дедуп | Jaccard по концептам | нет / по сущности |
| Обучение | веса концептов ± | правила (вручную) или веса внутри правил |
| Состояние в БД | таблица `interests` | своя таблица правил |

### План внедрения
1. **Шаг 1** — выделить `Strategy` интерфейс, переселить текущую логику в `FeedStrategy` без изменения поведения (чистый рефактор, проверка — бот работает как раньше).
2. **Шаг 2** — добавить столбец `channels.strategy` + registry.
3. **Шаг 3** — написать `WatchlistStrategy` с нуля, feed не трогая.

### Оговорки (честно)
- Проект маленький (~5 файлов). Абстракция окупается только когда стратегий ≥2 реально работают. Пока watchlist не написан — feed просто переезжает в класс без сиюминутной выгоды.
- Состояние стратегий разное → общая таблица не подойдёт, каждая владеет своими таблицами. БД-слой перестанет быть плоским.
- `analysis` разной формы → лучше каждая стратегия сериализует своё в `messages.analysis_json`, чем общий нетипизированный dict.
- **Не рефакторить, пока watchlist только «идея».** Преждевременная абстракция под одну реализацию мешает. Дешевле дописать watchlist грубо и вынести интерфейс, когда различия проявятся в бою.

## Управление watchlist (варианты UI)

Обсуждались, выбран гибрид:

| Вариант | + | − |
|---------|---|---|
| Команды бота (`/watch PS5 price<40000`) | ноль инфры, с телефона | сложные правила в одну строку неудобны |
| Wizard-диалог (ConversationHandler) | наглядно, без синтаксиса | больше кода, нудно для быстрой правки |
| Локальная веб-морда (FastAPI + HTML) | самое наглядное для сложных правил | отдельный процесс, с телефона только через туннель |
| **YAML-файл + watchdog** | быстро для IT-человека, git-версии, копипаст | не с телефона |
| Google Sheets бэкенд | отовсюду, привычный grid | внешняя зависимость, оверкилл |

**Выбранный подход — гибрид YAML + бот:**
- **YAML-файл** = источник правды. Быстрое добавление/правка сложных правил, git-версионирование, копипаст. Основной инструмент за компом.
  ```yaml
  - name: PS5
    keywords: [PlayStation 5, PS5]
    price_max: 40000
  - name: Авиа из Самары
    origin: Самара
    dest: [Москва, СПб]
  ```
- **`/watchlist` в боте** — только просмотр + тумблер пауза/вкл правила с телефона (не редактирование, а оперативный контроль).
- Wizard — добавить позже, если лазить в файл начнёт раздражать.
- Веб-морда — только если правил станут десятки и захочется дашборд с историей срабатываний.
